# Защита сайта «По пути» от перегрузки

## Что установлено в коде

- Caddy: 10 секунд на заголовки, 45 секунд на получение тела, 180 секунд на ответ, 30 секунд ожидания следующего запроса; заголовки до 16 КБ, тело до 8 МБ.
- Node: заголовки до 16 КБ / 80 полей, максимум 512 TCP-соединений, до 200 запросов на соединение, тайм-ауты и ограничение длины URL.
- Токеновые лимиты, разрешающие короткий всплеск: всего 120 запросов/с с запасом 600; на IP 30/с с запасом 180; API 8/с с запасом 60; страницы 2/с с запасом 30.
- Одновременно обрабатываются до 128 запросов, до 24 на IP, до двух загрузок изображений.
- Счётчики IPv6 объединяются по /64. Таблица клиентов ограничена 20 тысячами записей и очищается; при заполнении новые клиенты получают временный отказ, а не вытесняют старые ограничения.
- При превышении лимитов возвращается 429 или 503 с Retry-After. Избыточное тело — 413, слишком длинный URL — 414.
- Ограничения входа и заявок теперь учитывают IP посетителя, а не общий адрес Caddy. Caddy всегда перезаписывает X-PP-Client-IP значением remote_host. Присланный посетителем X-Forwarded-For не используется приложением.
- TRUST_CADDY=1 установлен только в production Compose. Это безопасно при существующей схеме: порт website не опубликован, все внешние запросы идут через Caddy; внутренние контейнеры считаются доверенными. Нельзя включать этот флаг у сервера, доступного клиентам напрямую.
- Сводка traffic_guard выводится раз в минуту только при блокировках; в ней нет IP, токенов и персональных данных.
- Заявки по-прежнему ограничены 20 попытками за 15 минут, ошибки входа — 8 за 15 минут. Большое число посетителей за одним NAT делит лимит.

Это защита приложения от части HTTP-флуда и истощения ресурсов. Она не поглощает каналозабивающие атаки, TLS-флуд и все распределённые атаки; перезапуск сбрасывает оперативные счётчики. Нет заявления о полной DDoS-защите.

## Применение на VPS

```bash
cd ~/Po_puti
sudo bash deploy/update.sh
```

Скрипт проверит конфигурацию Caddy до применения и дождётся healthcheck.
Не нужно менять DNS, открывать новые порты или менять SSH.

Проверка:

```bash
cd ~/Po_puti
docker compose -f compose.production.yaml ps
docker compose -f compose.production.yaml logs --since=15m website | grep traffic_guard
docker compose -f compose.production.yaml exec -T proxy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
```

Отсутствие строк traffic_guard означает отсутствие зарегистрированных блокировок за этот интервал, а не неисправность. Под нагрузкой 429/503 ожидаемы; сами по себе они не доказывают атаку.

## XorekCloud: что нужно подтвердить

На https://xorek.cloud/ru заявлена базовая защита от DDoS. Публичная страница не подтверждает условия конкретного VPS 150.241.97.74 и покрытие HTTP-флуда. Текст для обращения в поддержку (самостоятельно отправить из кабинета):

> Здравствуйте! У нас VPS в Германии с IP 150.241.97.74, сайт https://poputi-vmeste.ru, HTTPS на Caddy. Уточните, включена ли для этого IP постоянная DDoS-защита, какие атаки L3/L4 покрывает и защищает ли HTTP/HTTPS от L7-флуда? Какие ограничения, пороги, условия null-route и порядок обращения во время атаки? Есть ли отдельный WAF/reverse-proxy для сайта и что нужно для подключения?

Если L7 не входит, требуется внешний защитный прокси/WAF. Перед подключением нужно получить его официальные диапазоны адресов, настроить доверие к ним в Caddy, корректно передавать проверенный IP, проверить HTTPS и заявки, затем ограничить доступ к origin через firewall с сохранением SSH и проверки сертификатов. Не включать доверие ко всем X-Forwarded-For и не закрывать origin до проверки работы защиты.

## Проверки перед выпуском

Тест traffic-check проверяет изоляцию IP, отказ подменным заголовкам, IPv6 /64, восстановление лимита, параллельность и освобождение счётчиков, пределы памяти и загрузок. Дополнительно проверяются бронирование и SEO. Caddyfile проверен официальным бинарным Caddy локально. Дополнительный локальный тест с настоящим Caddy подтвердил перезапись подставного IP и ответ 429 при превышении лимита. Нагрузочные запросы к публичному VPS не отправлялись; включение защиты хостером требует его подтверждения.
